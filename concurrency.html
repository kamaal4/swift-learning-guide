Concurrency

How Swift runs many things at once without letting them trample each other's data. Every figure on this page moves: step through it, run it, cancel it, break it.

Based on The Swift Programming Language (6.4)13 sectionsRunnable code: ConcurrencyExamples.swift

Section 1

Why concurrency

In Swift, concurrency means two ideas used together:

  • Asynchronous code can pause partway through, say while it waits for the network, and carry on later. Only one piece runs at a time, but nothing sits idle.
  • Parallel code runs at the same moment on different CPU cores. Four cores, four pieces of code at once.

The extra flexibility has a price. You don't know ahead of time which code will run at the same moment, or in what order. When two pieces of code touch the same mutable data at the same time, that's a data race. With Swift's language support for concurrency, most data races become compile-time errors. The few the compiler can't see stop the program when they happen, instead of corrupting data quietly.

What about threads?

Swift's model is built on threads, but you never handle them directly. An async function can give up its thread while it waits, so other code can use that thread. When it resumes, it may be on a different thread: Swift makes no promise about which one.

In the kitchen

Without concurrency, a cook stands in front of the oven until the bread is done. With it, the cook slides the tray in, takes the next ticket, and comes back when the timer rings.

Key takeaway

Asynchronous means it can pause and resume. Parallel means it runs at the same time. Swift gives you both, and checks your code for data races.

Section 2

Async functions and await

An ordinary function runs to the end, throws an error, or never returns. An asynchronous function can do all of that, and it can also pause in the middle while it waits for something.

func listPhotos(inGallery name: String) async -> [String] {
    let result = // ... some asynchronous networking code ...
    return result
}

Write async after the parameters, before the ->, in the same place as throws. A function that does both is async throws. When you call one, you put await in front. await marks a possible suspension point: execution may pause there. Code never pauses anywhere else, so every place your function can pause is visible in the source.

Pausing at an await is also called yielding the thread: Swift parks your function and runs other code on that thread in the meantime.

Where you can write await

  • In the body of an async function, method or property.
  • In the static main() method of a type marked @main.
  • Inside an unstructured task, Task { … } (section 7).

await works like try, with one big difference

ThrowingAsynchronous
Mark the declarationthrowsasync
Mark the calltryawait
Can call others of its kindYesYes
Call it from code without the markerYes: wrap it in do/catch or ResultNo: there's no safe way to wait for async code from sync code

The standard library leaves out a "call this async function from sync code and wait" helper on purpose, because building one leads to subtle races, threading bugs and deadlocks. That decides how you add concurrency to an existing project: top-down. Convert the top layer first, then the layers it calls, one at a time.

While learning, Task.sleep(for:) is a handy stand-in for slow work: it pauses the current task for at least the given time. It can throw (it ends early if the task is cancelled), so you call it with try await, and the function becomes async throws:

func listPhotos(inGallery name: String) async throws -> [String] {
    try await Task.sleep(for: .seconds(2))
    return ["IMG001", "IMG99", "IMG0404"]
}

let photos = try await listPhotos(inGallery: "A Rainy Weekend")
In the kitchen

await is the oven timer. The ticket goes on the waiting shelf, the cook takes another ticket, and when the timer rings any free cook may pick yours back up.

Key takeaway

async marks a function that can pause; await marks every spot where it might. Sync code can't wait for async code, so convert from the top down.

Section 3

Async sequences

listPhotos hands back the whole array at once, after every element is ready. An asynchronous sequence hands you one element at a time, as soon as each one is available.

import Foundation

let handle = FileHandle.standardInput
for try await line in handle.bytes.lines {
    print(line)
}

A for await loop (for try await when the sequence can throw) may pause at the start of every iteration while it waits for the next element. To use your own type in one, conform it to AsyncSequence, the same way conforming to Sequence makes a type work in a plain for-in loop.

In the kitchen

An array is the whole tray arriving at once. An async sequence is a conveyor belt: you plate each dish the moment it rolls out.

Key takeaway

for await handles each element as it arrives, pausing between elements instead of waiting for all of them.

Run it: section 3 of ConcurrencyExamples.swift builds a small AsyncStream.

Section 4

Calling async functions in parallel

Three await calls in a row run one after another. Each download finishes before the next one starts, even though none of them depends on the others. Write async let instead and the call starts without waiting. All three downloads start at once and can run at the same time if the system has room. You write await only where you need the results.

await

When the next line needs the result

The work runs one step after another.

async let

When you need the result later

The work can run in parallel.

Both let other code run while they're waiting, both mark the waiting spot with await, and you can mix them freely in the same function.

In the kitchen

Sequential await: one dish into the oven, wait, take it out, next dish. async let: all three dishes go in together and you wait once, for the slowest.

Key takeaway

async let starts work now and collects it later. Total time becomes the slowest call instead of the sum of all of them.

Run it: section 4 of ConcurrencyExamples.swift measured 4.6s vs 2.0s.

Section 5

Tasks and task groups

A task is a unit of work that runs asynchronously, and all async code runs inside some task. A single task does one thing at a time, but Swift can run many tasks at once.

async let quietly creates a child task. When you don't know ahead of time how many children you need, use a task group: withTaskGroup creates one, and addTask adds a child. Every child in a group has the same parent, and children can have children of their own. Because these parent/child links are explicit, this style is called structured concurrency.

As soon as any child finishes, for await photo in group hands you its result. Nothing guarantees the order children finish in, so results arrive in completion order, not the order you added them. To return a value from the group, collect inside the closure:

let photos = await withTaskGroup(of: Data.self) { group in
    let photoNames = await listPhotos(inGallery: "Summer Vacation")
    for name in photoNames {
        group.addTask {
            return await downloadPhoto(named: name)
        }
    }

    var results: [Data] = []
    for await photo in group {
        results.append(photo)
    }

    return results
}
Throwing children

If the child tasks can throw, use withThrowingTaskGroup(of:returning:body:) instead.

In the kitchen

A big order is split into sub-tickets. The order can't go out until every sub-ticket is back, and if the customer leaves, every sub-ticket is binned.

Key takeaway

Task groups give you any number of child tasks. The parent always waits for its children, and cancellation, priority and task-local values flow through the tree.

Section 6

Task cancellation

Cancellation in Swift is cooperative. Cancelling a task doesn't stop it. It sets a flag, and the task's own code checks that flag at sensible points and decides how to stop. Usually that means one of three things:

  • throw an error such as CancellationError
  • return nil or an empty collection
  • return the work finished so far

The figure runs the book's cancellation-aware version of the group:

let photos = await withTaskGroup { group in
    let photoNames = await listPhotos(inGallery: "Summer Vacation")
    for name in photoNames {
        let added = group.addTaskUnlessCancelled {
            Task.isCancelled ? nil : await downloadPhoto(named: name)
        }
        guard added else { break }
    }

    var results: [Data] = []
    for await photo in group {
        if let photo { results.append(photo) }
    }
    return results
}
  • addTaskUnlessCancelled refuses to add new work once the group is cancelled, and returns false.
  • guard added else { break } stops the loop at that point.
  • Each child checks Task.isCancelled before downloading and returns nil if it's set.
  • The results skip the nils, so you keep a partial result instead of throwing away finished downloads.

In this example downloadPhoto doesn't check for cancellation itself, so a download that already started runs to the end. That's what "cooperative" means in practice.

try Task.checkCancellation()

Throws if the task is cancelled. The error carries out of the task and stops all of its work. Simplest to write.

Task.isCancelled

A Bool you check yourself, so you can clean up first: close connections, delete temporary files.

withTaskCancellationHandler

Runs a closure the moment the task is cancelled, for work that has to hear about it right away.

let task = Task {
    await withTaskCancellationHandler {
        // ...
    } onCancel: {
        print("Canceled!")
    }
}

// ... some time later...
task.cancel()  // Prints "Canceled!"
Two details

Even with a handler, cancellation stays cooperative. The handler runs while the task is still running, so don't share mutable state between the two. And to check a task from outside it, use the instance property task.isCancelled; inside, use the type property Task.isCancelled.

In the kitchen

The manager calls out "order cancelled!" Cooks finish the step they're on, check the board before starting anything new, and hand over whatever dishes are already done.

Key takeaway

Cancelling only raises a flag. Your code checks it with isCancelled or checkCancellation() and decides what to return, often a partial result.

Run it: section 6 of ConcurrencyExamples.swift cancels mid-loop and keeps 4 of 6 photos.

Section 7

Unstructured concurrency

Sometimes a task can't have a parent. A button tap, for example, is synchronous code that needs to kick off async work. An unstructured task has no parent. You get complete freedom in how you manage it, and complete responsibility for getting it right.

  • Task { … } creates a task that behaves like the code around it: same actor isolation, same priority, same task-local values.
  • Task.detached { … } creates a task that inherits none of those.

Both return a handle you can await for the result or cancel():

let newPhoto = // ... some photo data ...
let handle = Task {
    return await add(newPhoto, toGalleryNamed: "Spring Adventures")
}
let result = await handle.value
Task { }Task.detached { }
Has a parent taskNoNo
Inherits actor isolationYesNo
Inherits priorityYesNo
Inherits task-local valuesYesNo
Returns a handle (.value, .cancel())YesYes
In the kitchen

A child task is a sub-ticket clipped to its order. Task { } is a new ticket written at the same station, with the same notes. Task.detached is a ticket handed to the kitchen next door, which knows nothing about your station.

Key takeaway

Prefer structured tasks. Use Task { } to start async work from sync code, and Task.detached only when you really want a clean slate.

Section 8

Isolation

Splitting work into tasks is half the story. The other half is the data those tasks share, such as your app's UI state. Swift guarantees that while you read or change a piece of data, no other code is changing it at the same time. That guarantee is called data isolation, and data gets it in one of three ways:

immutable

It can't change

let label = "Outdoors"

Nobody can modify a constant, so reading it is always safe.

one task

Only this task can reach it

var total = 0  // local

No other code has a reference to a local variable. If a closure captures it, Swift makes sure that closure isn't run concurrently.

actor

An actor guards it

await logger.update(with: 31)

Code isolated to the actor can use its data safely. Everyone else waits for a turn.

Swift won't let you write the unprotected version

In Swift 6 mode, sharing a plain mutable class between tasks like this is a compile-time error. The figure shows the bug the compiler is preventing. Section 8 of the runnable file forces it with @unchecked Sendable: on our run, 10 tasks × 10,000 increments came out as 92,520 instead of 100,000.

In the kitchen

Two cooks keep a tally on a whiteboard. Both read 4, both write 5, and one order disappears. Hand the whiteboard to the cashier and make everyone ask the cashier to update it.

Key takeaway

Data is safe when it can't change, when only one task can reach it, or when an actor guards it.

Section 9

The main actor

An actor protects mutable data by making code take turns with it. In most apps the most important one is the main actor. It protects all the data your UI uses, and it takes turns rendering the UI, handling events, and running your code that reads or updates the UI. Until you start using concurrency, everything runs on the main actor. As you find slow work, you move it off.

Main actor vs main thread

Closely related, not the same thing. Code on the main actor runs on the main thread, which is why the two terms get mixed up. Your code works with the main actor; the main thread is a lower-level detail underneath it.

Mark a function @MainActor and it always runs on the main actor. From main-actor code you call it like any function. From anywhere else you need await, because switching to the main actor is a possible suspension point.

This is the everyday pattern: do slow work in the background, then switch to the main actor for the UI update. To make a closure run on the main actor, write @MainActor before in. Unlike downloadAndShowPhoto, this version doesn't wait for the UI update to finish:

let photo = await downloadPhoto(named: "Trees at Sunrise")
Task { @MainActor in
    show(photo)
}

Whole type or just some members

You often don't write @MainActor at all, because frameworks write it for you and it spreads:

Marked @MainActorAlso becomes @MainActor
a protocol: @MainActor protocol Viewtypes that conform: struct PhotoGalleryView: View
a base classits subclasses
a property wrapper's wrappedValueevery property that uses the wrapper

So in SwiftUI, your views and their state properties are already on the main actor.

In the kitchen

Only the front counter serves customers. Food is cooked in the back; when it's ready, it waits for a free moment at the counter to be handed over.

Key takeaway

Do slow work off the main actor, then await a @MainActor function to touch the UI. Frameworks like SwiftUI already put your views on the main actor.

Section 10

Actors

Swift gives you the main actor, and you can define your own. Like classes, actors are reference types. Unlike classes, an actor lets only one task at a time touch its mutable state, so code in many tasks can safely share one actor instance.

actor TemperatureLogger {
    let label: String
    var measurements: [Int]
    private(set) var max: Int

    init(label: String, measurement: Int) {
        self.label = label
        self.measurements = [measurement]
        self.max = measurement
    }
}

extension TemperatureLogger {
    func update(with measurement: Int) {
        measurements.append(measurement)
        if measurement > max {
            max = measurement
        }
    }
}

From outside, reading a property means await: if another task is using the logger right now, you wait your turn. Code inside the actor, like update(with:), uses the properties directly with no await.

compile error
print(logger.max)

error: actor-isolated property 'max' cannot be accessed from outside of the actor

works
print(await logger.max)
// Prints "25"

A possible suspension point: you may wait for the actor to be free.

Only code running on an actor can touch that actor's state. That guarantee is called actor isolation. Why one task at a time? Because updates often break an object's rules for a moment. Halfway through update(with:), the new reading is already in the array but max hasn't caught up.

Three guarantees that work together

  1. Code between two possible suspension points runs in sequence, without being interrupted by other concurrent code.
  2. Code that touches an actor's state runs only on that actor.
  3. An actor runs only one piece of code at a time.

So keep any step that temporarily breaks the rules free of await. Better still, put it in a synchronous method. A sync method can never contain a suspension point, and if someone later adds an await to it, they get a compile error instead of a bug:

extension TemperatureLogger {
    func convertFahrenheitToCelsius() {
        for i in measurements.indices {
            measurements[i] = (measurements[i] - 32) * 5 / 9
        }
    }
}

Halfway through that loop, some readings are Fahrenheit and some Celsius, and nobody else can see it.

In the kitchen

The cashier serves one customer at a time. Nobody gets to peek at the till while it's being counted.

Key takeaway

An actor is a reference type that serves one task at a time. Access from outside needs await. Keep temporarily broken state between two awaits, never across one.

Run it: section 10 of ConcurrencyExamples.swift. Uncomment print(logger.max) to see the error yourself.

Section 11

Global actors

The main actor is a single, global instance of the MainActor type. A normal actor type can have many instances, each with its own isolated state, so to use one you need to say which instance. MainActor only ever has one instance, so the type name alone identifies it. That's why it can be used as an attribute.

You can create your own singleton actor with @globalActor and use it the same way:

@globalActor
actor PhotoLibraryActor {
    static let shared = PhotoLibraryActor()
}

@PhotoLibraryActor
enum PhotoLibrary {
    static var saved: [String] = []
    static func save(_ name: String) { saved.append(name) }
}

await PhotoLibrary.save("IMG001")

Key takeaway

A global actor is a singleton actor you apply as an attribute. @MainActor is the one you'll use most.

Run it: section 11 of ConcurrencyExamples.swift.

Section 12

Sendable types

Tasks and actors divide a program into pieces that can safely run at once. The part of a task or actor that holds mutable state is called a concurrency domain. Some data can't be shared between domains: it has mutable state and nothing stopping two pieces of code from changing it at once.

A type that can be passed from one domain to another, as an argument to an actor method or as a task's result, is sendable. You mark it by conforming to the Sendable protocol. The protocol has no methods, but Swift enforces its rules. A type is sendable in one of three ways:

A value type of sendable parts

A struct whose stored properties are sendable, or an enum whose associated values are.

No mutable state at all

A struct or class with only read-only properties, all of them sendable.

It protects its own state

A @MainActor class, or a class that serializes access on a particular thread or queue.

struct TemperatureReading: Sendable {
    var measurement: Int
}

extension TemperatureLogger {
    func addReading(from reading: TemperatureReading) {
        measurements.append(reading.measurement)
    }
}

let logger = TemperatureLogger(label: "Tea kettle", measurement: 85)
let reading = TemperatureReading(measurement: 45)
await logger.addReading(from: reading)

A struct or enum that isn't public and has only sendable parts is sendable automatically, so writing : Sendable above is optional. To opt a type out explicitly, write an unavailable conformance:

struct FileDescriptor {
    let rawValue: Int
}

@available(*, unavailable)
extension FileDescriptor: Sendable {}
Going further

Swift 6 also lets you hand off a non-sendable value that nothing else uses afterwards (region-based isolation). It complains only when the value could be used on both sides at once, with an error like "sending value of non-Sendable type … risks causing data races". Sendable is about values that are safe to share.

In the kitchen

Passing a sealed takeaway box from one station to another is fine. Passing a pot that two cooks will stir at the same time is not.

Key takeaway

Sendable means safe to share between tasks and actors: value types of sendable parts, types with no mutable state, and types that protect their own state.
